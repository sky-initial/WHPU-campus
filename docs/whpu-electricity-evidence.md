# 电费网页入口核验

## 2026-11-14：内置页面与外部访问差异

用户确认外部浏览器能正常访问电费查询页，WHPU Pocket 内不能进入。OPD2407 / Android 16 上进行了以下核验，没有输入房间、提交缴费或保存认证参数。

- 今日校园已有登录态可进入“服务 → 虚拟校园卡 → 电费缴纳”。其“其他楼栋（电费充值）”正常显示选择校区、楼栋、楼层、房间及确认信息的表单。其他两个分组分别为“金银湖校区（6，7，8）栋照明电费充值”和“常青1号楼、金湖10栋、11栋电费充值”，不能用第一组结果替代它们的验收。
- 修复前 WHPU WebView 使用 `X11; Linux x86_64` 的 PC 标识。同一校园卡登录态下，点击第一组产生 `GET /charge/feeitem/toAppitem`，随后导航至 `/plat-pc/notfound`。错误页面的 HTTP 状态是 200；页面异常不能等同于请求返回 HTTP 404。
- 同一 WebView、同一登录态，临时使用 Android Mobile 标识并完整重载分组页后，点击相同分组导航至 `/charge-app/`，返回 HTTP 200，并显示四级选择表单。测试在同一调试连接内保持标识，结束后恢复，未修改 Cookie、Token 或认证存储。
- 再从正式门户 `https://e.whpu.edu.cn/` 全程使用移动端标识，门户加载 `/CUS_TEMPLATE_WORK/mobile/index.html`，通过“服务 → 虚拟校园卡”成功交接至校园卡业务页，电费三组入口可见。移动门户的导航名称为“服务”，与 PC 门户的“服务中心”不同。

上述对照支持修复 PC 标识导致的错误导航，不再将学校电费整体不可用作为结论。公网入口继续使用融合门户，不能把临时认证跳转地址或带认证参数的查询地址写入固定入口。

## 实现与验证范围

校园卡与电费 WebView 在第一次导航前使用移动端浏览器标识，保留设备 Android 信息和实际 Chromium 版本；平板也保留 Mobile 标识。门户及后续业务使用同一标识，不在登录重定向过程中切换。座位预约、允许域名、HTTPS 限制、认证存储和原生校园卡缓存策略保持原有实现。

Android 官方说明，加载过程中修改 User-Agent 会触发重新加载，因此本次在 WebView 初始化时统一设置：[WebSettings.setUserAgentString](https://developer.android.com/reference/android/webkit/WebSettings#setUserAgentString(java.lang.String))。

修复后验证：

- 548 项单元测试通过，失败、错误和跳过均为 0；Debug 和测试 APK 构建成功。
- OPD2407 覆盖安装，没有卸载；安装前后 4 个数据库/DataStore 文件在内存中逐字节比对一致，没有导出真实数据。
- 6 项网页生命周期和 1 项人工认证交接设备回归通过。两项新增导航用例检查真实 WebView 请求头与 JavaScript 的 Android Mobile 标识、跨域前进、返回及返回入口；初次通过前进与标识断言，但 JavaScript 模拟点击后的返回失败。改为原生触摸链接后，两项复测均通过，保留原返回断言；没有修改生产返回逻辑。共 9 项相关设备用例最终通过，首次失败日志保留。
- 安装后的修复 APK 未启用调试 UA 覆盖，从校园卡入口及独立“宿舍电费”入口分别经移动门户“服务”进入虚拟校园卡，再进入“其他楼栋”表单成功。另两组也分别进入 `/charge-app/`：金银湖 6、7、8 栋组显示楼栋、楼层、房间选择，常青 1 号楼/金湖 10、11 栋组显示楼层、房间选择。没有选择房间或提交缴费。
- 返回校园卡官方首页，点击“同步余额与账单”回到原生页，再手动刷新成功。内存中核对原生余额与官方余额、流水条数与官方总数，一致；仅保存布尔结果。

以上为平板 Debug 修复版验证，正式 rc6 尚不包含本修复。正式候选版需在 PR 合并后从主线构建和发布。

## 原生查询仍需核验

网页导航修复不提供原生电费余额，不恢复后台采样。后续已核验公共目录及用户授权房间的金额结果，见下节；原生认证交接、错误与空结果语义仍需补齐。缴费由用户在官方页面完成。

## 后续只读目录与房间查询证据

用户明确授权选择自己的房间，并确认查询的是金额。本节只记录结构和脱敏显示模板，不记录房间地址、目录标识、实际余额或认证值；没有绑定房间或发起支付。

### 请求与目录

实际观察的目录和房间查询均为 `POST https://ecardapp.whpu.edu.cn/charge/feeitem/getThirdData`，`Content-Type: application/x-www-form-urlencoded`。学校前端带 `Authorization` 与 `synjones-auth` 请求头。另观察到配置查询 `GET /charge/feeitem/singleFeeitem?feeitemid=...`，不能从配置字段名称直接推断金额单位。“其他楼栋”实际收费项目 ID 为公开目录编号 `182`，查询页标题为“常青校区，金银湖校区”。

目录请求参数为 `feeitemid`、`type=select`、`level`，加上此前已选层级的 `code=value`。初始 `level=0`；选第一层后为 `1`，依次递增。HTTP 200、业务 `code=200` 的成功目录包含 `map.total[]`（`code`、`level`、`name`）与 `map.data[]`（`name`、`value`）。本次未见分页字段，但未把这一现象推定为所有接口均无分页。

三个分组的实际层级不同：

| 官方分组 | `map.total` 的 code / 名称 / level |
| --- | --- |
| 其他楼栋 | campus / 校区 / 1；building / 楼栋 / 2；floor / 楼层 / 3；room / 房间 / 4 |
| 金银湖 6、7、8 栋照明 | building / 楼栋 / 1；floor / 楼层 / 2；room / 房间 / 3 |
| 常青 1 号楼、金湖 10、11 栋 | campus / 公寓 / 1；building / 楼层 / 2；room / 房间 / 3 |

第三组首层只有一个选项时，官方页面自动选中并请求下一层。不能硬编码 `building` 一定代表楼栋，也不能以可见控件数代替完整请求层级。

“其他楼栋”已逐级核验两个校区的楼栋目录，以及一个授权楼栋的楼层和房间列表。照明、空调分别作为不同楼栋选项，房间标签格式也可能不同；缓存分区必须包含服务分组与完整选择路径，不能仅以房间显示名或房号归并。

### 金额结果

用户授权房间的照明和空调均经官方选择器查询成功。房间选定后，官方页面直接请求 `type=IEC`、`level=4`，携带 `feeitemid,campus,building,floor,room`；没有额外发送一次 `type=select,level=4`。成功响应为 `code=200`、`map.showData.信息` 字符串，以及 `map.data` 的房间上下文。

两项结果的脱敏显示模板均为 **当前房间余额为<数值>元**。官方前端将 `showData` 赋给 `aboutEleric.electricInfo` 后展示；实际页面与响应一致。只确认此分组和本次两项结果为人民币金额，不换算为电量，不用充值金额推算余额。其他分组的金额格式尚未实查。

`map.data` 观察到 `area,buildingName,areaName,floorName,floor,aid,account,building,room,roomName`，不能把其中 `account` 默认当成校园卡账号。原生查询仍须单独确认登录身份与选择路径的归属。

核验期间空调房间标签多出楼栋前缀，首次选择未匹配后，连续脚本仍执行了默认项确认；该次结果未保存数值、不计为授权房间验收。随后改为选择成功后单独执行确认，精确匹配用户指定房间，并在内存中核对匹配结果、页面显示与未绑定状态。后续自动化须在选择失败时停止，不能继续确认默认选项。

### 认证与项目目录补查

- 最小认证核验：官方公开前端以自身状态中的 token 组装 bearer 请求头；在浏览器内比较，该状态与现有校园卡交接来源相同，只输出相等结果。对同一公共目录请求，不带任何认证和 Cookie 时返回 HTTP 200、业务 `code=401,success=false`；只带现有 `synjones-auth` bearer 头、不带 Cookie 或额外 Authorization 头时返回 HTTP 200、`code=200,map` 和完整初始目录。没有读取到本地、打印或保存令牌，也没有清除页面登录态。该结果支持复用校园卡会话，原生端仍须实测；无凭据响应不替代自然过期验收。
- 官方公开前端存在 `/feeitem/showFeeitem` 方法，但本次通过其客户端调用进入错误回调，未取得项目列表；不将代码中出现的路径记为已验证可用目录。三个分组仍以实际门户菜单为依据。
