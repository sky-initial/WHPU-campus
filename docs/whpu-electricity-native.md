# WHPU 电费原生查询进度

PR #25 已合并，接通“其他楼栋”的原生选择、余额查询、账号与房间缓存、今日页及只读小组件，已在 rc8 发布。2026-11-15 的切片增加“金银湖 6、7、8 栋照明”原生查询，PR #32 / #33 合并后已在 rc10 发布。2026-11-16 切片接通“常青 1 号楼、金湖 10、11 栋”的官方原值查询，单位仍未确认，详见末节；尚未发布。

## 已有实现

- 复用现有校园卡内存会话，电费 Provider 只调用学校当前用户和 `getThirdData` 两个只读接口；不创建支付，不绑定房间，不读取旧郑大缓存。
- 目录按返回的 `code/name/level` 解析，支持不同分组的层级命名；原样保留选项 value，通过表单编码发送，不能把其中的 `&` 当作额外表单字段。
- 查询按收费项目使用对应映射：`182` 为四层、“当前房间余额为…元”；`201` 为三层、“当前房间当前剩余金额…元”。目录层级、选择路径与返回房间上下文一致后保存精确人民币数值字符串；201 实际返回四位小数，不舍入到整数分。项目 `1` 按“公寓 → 楼层 → 房间”查询，官方标为“当前剩余电量”的原值使用独立类型，不写入人民币字段。
- 查询前后核对校园卡服务账号身份及会话代次；换账号、并发更换会话、HTTP 错误、业务 401、解析错误不产生成功快照。错误文案不包含学校原始响应。
- 复用 Room 的 `kv_cache`，每个账号一个完整快照，内部按收费项目与完整房间路径保存独立余额和时间；刷新失败保留旧结果，成功零余额正常更新。账号指针与快照事务提交，不增加数据库版本，不采用旧电量缓存。

## 182 字段依据（rc8 历史验收）

用户授权房间的空调查询中，在浏览器内逐字段比较后确认：选择器的 value 由“编号&名称”组成；campus 对应返回的 area/areaName，building 对应 building/buildingName，floor 对应 floor/floorName，room 对应 room/roomName。只输出匹配布尔值，不记录真实字段值。

同一授权房间使用当前 bearer 头、不携带 Cookie 或额外 Authorization 头重复只读查询，业务返回成功；金额与官方页面一致，返回上下文与请求选择路径一致，未绑定房间。随后在 OPD2407 上完成 Android 学校页面到共享内存会话的交接，原生 OkHttp 目录和授权空调房间余额查询成功；以同一已登录官方页面发起只读查询，在内存比较原生金额与网页响应，金额、人民币单位及房间上下文均一致。未导出真实金额、房间结果或登录凭据。

## 金银湖照明分组扩展（2026-11-15 开发，rc10 已发布）

项目 201 的三层目录、完整人民币模板及返回房间编号/名称已通过真实只读查询核验，见[新增证据](whpu-electricity-evidence.md#2026-11-15另外两个分组的只读结果核验)。原生选择、前进和返回上一层始终携带所选项目 ID；不再默认回到 182。两个分组各用自己的金额模板和完整上下文映射，复用账号与房间缓存及今日页/组件数据源，Room 仍为版本 10。

金额由整数分改为精确人民币数值字符串 `balanceYuan`。解析使用 BigDecimal，显示至少两位小数并保留全部有效精度，今日页与小组件读取同一字符串。缓存读取兼容 rc8/rc9 的 `balanceFen`，精确转换后保留原账号、房间、当前选择和更新时间；选择或刷新时写入新格式，不修改 Room 表结构。旧客户端不支持新金额载荷，因此本次不将安装旧 APK 读取新缓存列为兼容承诺。

该切片发布时，项目 1 的官方结果写“当前剩余电量”，没有明确计量单位，保留官方入口。2026-11-16 的后续实现见下节，仍不按人民币解释或换算为度数。

- 专用 API 31 模拟器 **20 项设备回归通过**：电费缓存 15、原生电费界面 2、小组件渲染 3。包括旧整数分载荷读取、新旧分组并存、四位小数及微小负数重开保留、选择回退保留分组、503 失败保留、两种组件宽度和浅深色的金额显示。测试后恢复原正式 rc8、原数据库及 DataStore 字节，系统免打扰状态保留，模拟器暂停。
